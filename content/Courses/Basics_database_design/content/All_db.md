# Классификация Баз Данных

Базы данных классифицируются по нескольким ключевым признакам. Вот основные виды, которые важно знать в контексте дисциплины «Технология разработки и защиты баз данных».

---

## 📊 1. По модели данных (самый важный критерий)

Этот критерий определяет **как именно организованы данные** внутри БД.

### 🔹 Реляционные (RDBMS)
**Суть:** Данные хранятся в виде таблиц (отношений), связанных между собой через ключи. Строгая схема, язык запросов — SQL.

**Примеры:** PostgreSQL, MySQL, Oracle Database, Microsoft SQL Server, SQLite.

**Плюсы:**
- Строгая целостность данных (ACID).
- Зрелые технологии, огромное сообщество.
- Стандартизированный язык SQL.

**Минусы:**
- Плохо масштабируются горизонтально (на тысячи серверов).
- Жёсткая схема — сложно менять структуру на лету.

**Когда использовать:** Финансы, ERP, CRM, учётные системы — везде, где важна точность и целостность.

---

### 🔹 Нереляционные (NoSQL)
**Суть:** Отказ от табличной модели и жёсткой схемы. Данные хранятся в более гибких форматах. Подразделяются на подтипы:

| Подтип | Модель хранения | Примеры | Для чего |
|--------|-----------------|---------|----------|
| **Документоориентированные** | JSON-подобные документы | MongoDB, CouchDB | Каталоги, профили пользователей, CMS |
| **Ключ-значение (Key-Value)** | Пары «ключ → значение» | Redis, Memcached, DynamoDB | Кэши, сессии, очереди |
| **Колоночные (Column-family)** | Данные по колонкам, а не строкам | Cassandra, HBase | Big Data, аналитика, временные ряды |
| **Графовые** | Узлы и рёбра (связи) | Neo4j, ArangoDB | Соцсети, рекомендации, маршруты |

**Плюсы NoSQL:**
- Гибкая схема (можно менять поля на лету).
- Горизонтальное масштабирование (шардирование).
- Высокая скорость для специфических задач.

**Минусы:**
- Часто нет ACID (или только частично).
- Нет единого стандарта языка запросов.
- Сложнее обеспечивать целостность.

**Когда использовать:** Big Data, реальное время, соцсети, IoT, кэширование.

---

### 🔹 Объектно-ориентированные (OODB)
**Суть:** Данные хранятся в виде объектов, как в ООП-языках (Java, C++). Поддерживают наследование, инкапсуляцию, полиморфизм.

**Примеры:** ObjectDB, db4o, GemStone/S.

**Плюсы:** Нет «расхождение импедансов» (impedance mismatch) между кодом и БД.
**Минусы:** Сложны в запросах, мало распространены.

**Когда использовать:** САПР, научные расчёты, сложные инженерные системы.

---

### 🔹 Объектно-реляционные (ORDBMS)
**Суть:** Гибрид — реляционная модель + объектные расширения (свои типы данных, наследование таблиц, массивы).

**Примеры:** PostgreSQL (с расширениями), Oracle (объектные типы).

**Когда использовать:** Когда нужна мощь SQL и гибкость объектов.

## 🗂️ 2. По способу хранения и доступа

| Вид | Описание | Примеры |
|-----|----------|---------|
| **Централизованные** | Одна БД на одном сервере | Классический PostgreSQL |
| **Распределённые** | Данные хранятся на нескольких серверах, но выглядят как единая БД | Google Spanner, CockroachDB |
| **Файл-серверные** | Файлы БД лежат на общем диске, обработка — на клиентах | Microsoft Access |
| **Клиент-серверные** | Сервер обрабатывает запросы, клиент — только интерфейс | PostgreSQL, MySQL |
| **Встраиваемые (Embedded)** | БД работает внутри приложения, без отдельного сервера | SQLite, Firebird |

---

## 🌐 3. По масштабу и назначению

| Вид | Описание | Примеры |
|-----|----------|---------|
| **OLTP (Online Transaction Processing)** | Много коротких транзакций (вставка, обновление). Акцент на скорости и целостности | PostgreSQL, MySQL в интернет-магазине |
| **OLAP (Online Analytical Processing)** | Аналитические запросы по большим объёмам данных. Акцент на чтении и агрегации | ClickHouse, Amazon Redshift, Snowflake |
| **Хранилища данных (Data Warehouse)** | Централизованное хранилище для аналитики, собранное из разных источников | Snowflake, Google BigQuery |
| **Озёра данных (Data Lake)** | Сырые данные в любом формате, без схемы | Hadoop HDFS, Amazon S3 + Athena |
| **Базы знаний** | Хранение фактов и правил для экспертных систем | RDF-хранилища, GraphDB |

---

## 🏢 4. По среде использования

| Вид | Описание |
|-----|----------|
| **Локальные** | На одном компьютере, один пользователь |
| **Сетевые** | Доступ по сети для нескольких пользователей |
| **Облачные (DBaaS)** | Предоставляются как сервис: AWS RDS, Azure SQL, Google Cloud SQL |
| **Мобильные** | Встраиваемые БД для смартфонов: SQLite, Realm |

---

## 🔐 5. По уровню защиты (важно для вашей дисциплины)

| Вид | Описание |
|-----|----------|
| **С открытым доступом** | Любой может читать/писать (учебные примеры) |
| **С разграничением прав** | Роли, привилегии, аудит (production-системы) |
| **С шифрованием** | TDE (Transparent Data Encryption), шифрование на уровне столбцов |
| **С аудитом** | Логирование всех действий пользователей |
| **Соответствующие стандартам** | GDPR, HIPAA, PCI DSS — требования к защите персданных |

## 📌 Сводная таблица: что выбрать?

| Задача | Рекомендуемый тип БД |
|--------|----------------------|
| Интернет-магазин, банк | Реляционная (PostgreSQL, MySQL) |
| Кэш, сессии | Ключ-значение (Redis) |
| Каталог товаров с гибкой схемой | Документоориентированная (MongoDB) |
| Соцсеть, рекомендации | Графовая (Neo4j) |
| Аналитика по терабайтам | Колоночная (ClickHouse, Cassandra) |
| Мобильное приложение | Встраиваемая (SQLite, Realm) |
| Big Data, логи | Data Lake (Hadoop, S3) |

## 🎯 Что важно запомнить

1. **Реляционные БД** — основа основ, 80% рынка. Учить нужно в первую очередь.
2. **NoSQL** — не «замена», а «дополнение». Выбираются под конкретную задачу.
3. **Выбор БД** зависит от: объёма данных, скорости, целостности, масштабируемости, команды.
4. **Современный тренд** — гибридные решения (NewSQL: CockroachDB, TiDB), которые берут лучшее из обоих миров.
